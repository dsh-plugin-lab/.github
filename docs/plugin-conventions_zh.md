# 仓通用约定

[English](plugin-conventions.md) | [中文](plugin-conventions_zh.md)

**本文写给谁**：你正在看本组织的某个仓，需要判断某件事**算不算缺陷** —— 某个 PR 改了版本号、
某次发布读错了东西、两个仓不再长得一样、某个插件发出去的包里不再带市场需要的东西。**第 5 节是真正
要用的部分**：它很短，而且最后一列写明每条判据由哪个文件或脚本判，判「这条到底有没有被执行」从此有
答案而不是靠感觉。从那里开始。
**本文不写给**：在某个仓里怎么干活（那个仓的 `AGENTS.md`）、怎么贡献（本组织的 `CONTRIBUTING.md`）、
某次发布具体怎么跑（那个仓的 `docs/PUBLISHING.md`）、本组织仓自己怎么维护（它的 `AGENTS.md`）。
**不进本文**：论证、权衡与复盘 → [.agents/notes/](../.agents/notes/)。本文只留判据、每条一行意图、
重开条件、核对方法与指针。

## 三类仓

两层，一条规矩只对它所讲的那一层生效。

| 仓 | 产出 | 适用哪些节 |
|---|---|---|
| **插件仓** —— 一个插件一个仓 | 一个 npm 包，同时是一个 DSH bundle | 全部 |
| **组织仓**（`dsh-plugin-lab/.github`） | 不发布任何东西；提供回退件，并给新仓播骨架 | 一、二，以及第 5 节的卫生类判据 |
| **市场**（`dsh-plugin-lab/market`） | 一份生成的索引，由 GitHub Pages 提供；无包、无版本 | 一、二，作为**消费者**的第 4 节，以及第 5 节的卫生类判据 |

意图：组织仓与市场是**管理层设施** —— 它们因为存在插件才存在，本身不是插件。所以第 3 节的插件形状、
第 6 节的发布底线对它们不适用：把那些套到一个不发布任何产物的仓上，只会造出没人能满足的义务。
但它们仍是本组织的仓，所以「一个仓怎么维护」—— 回退件、CI、钩子、格式化、frozen 安装 —— 照旧全部适用。

判断一个文件该放哪，按顺序问三个问题：

1. **机制支不支持回退？** 支持 → 放组织仓（它的 `.github`），各插件仓代码零改动。
2. **内容通用、但机制不支持？** → 各仓独立，形状写进本文。
3. **内容仓特有？** → 各仓独立，本文不管。

---

## 一、能回退的：放组织仓

GitHub 只在平台支持的位置读这些文件，且**各仓有同名文件时用自己的**。新增仓因此自动继承，且不产生任何提交。

| 文件 | 放哪 | 作用范围 |
|---|---|---|
| `SECURITY.md` | 仓根 | 未自带该文件的仓 |
| `CODE_OF_CONDUCT.md` | 仓根 | 同上 |
| `SUPPORT.md` | 仓根 | 同上 |
| `CONTRIBUTING.md` | 仓根 | 同上 |
| `PULL_REQUEST_TEMPLATE.md` | 仓根 | 同上 |
| `.github/ISSUE_TEMPLATE/*.yml` | **必须在 `.github/ISSUE_TEMPLATE/`** | 同上；某仓一旦自建该目录，本仓模板对它**整体失效** |
| `.github/release-drafter.yml` | 组织仓 | 未自带配置的仓 |
| `profile/README.md` | `profile/` | 组织主页，不属回退机制 |

四条由机制推出的判据：

- **issue 模板必须在 `.github/ISSUE_TEMPLATE/` 下** —— 放仓根不生效，只认那一个路径。症状是「新建 issue 只有空白」，且**不报错**。
- **没有多语言机制** —— `CONTRIBUTING_en.md` 这类名字不被识别；要双语只能写在同一份文件里，不能靠第二份文件。
- **回退只在「本仓没有同名文件」时发生** —— 各仓已有自己的 `CONTRIBUTING.md` 时，组织仓那份永远不会被显示；它服务的是**将来新建的仓**。
- **`SECURITY.md` 写的私密报告入口**是各仓 **Security → Report a vulnerability**，需要各仓单独开启（**私有仓不需要**：仓本身就是私有的）。

## 二、通用但不抽

**`workflow` 类明确不抽**：不做 `workflow_call`；各仓自带一份，靠**形状**一致，不靠字节一致。

- **意图**：否则一处改动会同时改变所有仓 —— 且在各仓的 diff 里看不见 —— 还要多出一层跨仓排障。
- **逐字节相同是例外，不是通例。** 只有草稿 Release 的 workflow 要求同一份；`ci.yml`、`release.yml`、
  `compat.yml` 靠**形状**一致，参数按仓不同（job 矩阵、额外的腿、仓特有的步骤）。哪些文件才是候选，
  唯一真源是 `scripts/scaffold.mjs` 里的 `IDENTITY_FILES` —— 不是散文，也不是本文。
- **重开条件**：插件仓数量达到 6 个以上，或某个 workflow 开始出现真实的分支逻辑与多仓参数。
- 论证与被否掉的选项 → [决策：workflow 不抽成可调用 workflow](../.agents/notes/2026-10-12-workflow-copies-not-extracted.md)。

**脚手架只播种，不同步**：`scripts/scaffold.mjs` + `templates/plugin/` 只给**新仓**铺一次骨架，
之后**永不回写**任何已存在的仓。它的 `check` 子命令就是逐字节相同那条判据的执行体；`--verify`
在临时目录里生成一遍、跑生成仓自己的检查，模板改动以它为准。
论证 → [决策：脚手架只播种、不同步](../.agents/notes/2026-10-12-scaffold-seeds-not-syncs.md)。

**载体状态**：不建共享包、不抽副本。知识类靠指针（宿主官方真源），断言类走各仓各写、接受双向同步。

## 三、脚手架产出的形状

**这是目标，不是「四仓都这样」的声明。** 下面写的是 `node scripts/scaffold.mjs` 产出什么、为什么；
四个现有仓在哪些地方合法地不同，见 3.9。形状对不等于没问题，形状不同也不等于缺陷 —— 必须一致的东西在第 5 节。

**新仓不从本文抄形状**：形状由脚手架铺（`node scripts/scaffold.mjs <dir>`，随后 `--verify` 跑生成仓
自己的检查）。读本节是为了知道**为什么**生成出来的文件长这样、**哪里可以合法地不同** —— 不是拿来抄。
**已有仓拿本文当参照**：形状是什么，哪些部分不可协商。

### 3.1 CI 的收口 job

各仓 `ci.yml` 的最后一个 job：让 ruleset 只盯一个状态检查名，内部 job 增删都不必动 ruleset。

四条不能动：

- **只在 step 层判** —— 在 job 层，条件为假会让该 job 变成 `skipped`，而 GitHub 把 `skipped` 当成功。意图：不给假绿。
- **`needs` 必须列全本文件的每个 job id** —— 漏一个，那个 job 可以红着而收口 job 照常通过。
- **`if: always()`** —— 否则上游失败会把收口 job 本身一起跳过。
- **`skipped` 与 `failure`、`cancelled` 同等判红** —— 没跑过的 job 不能算通过。

```yaml
  ci-success:
    name: CI Success
    runs-on: ubuntu-latest
    needs: [<all job ids in this file>]
    if: always()
    steps:
      - name: Verify all jobs succeeded
        if: contains(needs.*.result, 'failure') || contains(needs.*.result, 'cancelled') || contains(needs.*.result, 'skipped')
        run: |
          echo "::error::some job did not succeed — CI Success goes red"
          echo '${{ toJSON(needs) }}'
          exit 1
```

ruleset 的 `required_status_checks` 只写 `CI Success` 这一个名字。

### 3.2 依赖漂移巡检

只开 `github-actions` 这一个生态。意图：本族的 npm 依赖大多跟着宿主的预发布线走，自动 PR 只会是噪音。

```yaml
version: 2
updates:
  - package-ecosystem: github-actions
    directory: '/'
    schedule:
      interval: weekly
      day: monday
    commit-message:
      prefix: ci
    groups:
      actions:
        patterns: ['*']
```

### 3.3 草稿 Release

**workflow** 每仓一份，要求逐字节相同：

```yaml
name: release-drafter

on:
  push:
    branches:
      - main
  workflow_dispatch:

permissions:
  contents: write

jobs:
  update-draft:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: release-drafter/release-drafter@v7
```

- **runner 必须钉 ubuntu**。意图：windows runner 上该 action 找不到配置文件，草稿静默为空且**不报错**（action 的大版本跟着上游走）。
- 草稿汇总的是**PR**，不是 commit：直接推到 `main` 的提交它看不见。这是取舍，不是缺陷。

**配置**分两层，落点不同：

- **形状是共享的**（在组织仓 `.github/release-drafter.yml`，未自带配置的仓回退到它）：草稿名、变更行
  `- $TITLE (#$NUMBER) @$AUTHOR`、转义集合、版本解析。**各仓不重新决定这些。**
- **分类 → 标签的映射按仓自定**。标签是**仓的元数据**，本来就会不同。组织仓那份是**默认值，不是标准**：
  标签不一样的仓自带一份配置。

**`tag-template: 'next'` 不属于可协商的那一层**（不像分类）：发布流程按这个 tag 读草稿。改它不是改配置，
是改所有读它的发布流程。

### 3.4 包管理器与构建

全族只有**一个包管理器**：pnpm，`pnpm-lock.yaml` 是唯一锁文件。没有第二个；清安装残留的脚本只清
`pnpm-lock.yaml`，因为没有别的东西可清。

- **`pnpm-workspace.yaml` 声明单包工作区。** 意图：不声明时 pnpm 把这个目录当非工作区目录，依赖树与 CI 装的那棵对不上。
- **安装带 `--config.node-linker=hoisted`。** 意图：pnpm 的 symlink linker 在这棵树上解不开浏览器半边的同侪包，失败表现为「测试看不见自己的依赖」。
- **CI 里 `pnpm/action-setup` 排在 `actions/setup-node` 前面。** 意图：反了 `cache: pnpm` 找不到 store。
- **本地钩子走 `pnpm exec`，不走 `npx`**，且带 `--config.verify-deps-before-run=false`。意图：它借树里**已有的**工具，一个字节都不下载。
- **构建器按仓自定**（见 3.9）。脚手架发的是 `tsdown`，两份配置在 `tsdown.config.ts`（宿主半边 ESM、
  浏览器半边 CJS 信封，浏览器半边的 CSS Modules 是那里的一个插件）；仓也可以直接跑编译器、用脚本产出浏览器半边。
  两者都满足判据；新仓从脚手架那个起步。

### 3.5 TypeScript 与测试骨架

- 每个编译目标一份 tsconfig，日常与契约**两套** vitest 配置分开。**数量各仓不同**（见 3.9）；必须一致的是：
  契约用例**显式排除**在日常配置之外，契约配置单跑（不并行、超时放宽）。
- `strict` 必须开。编译器开关负责类型与死代码，ESLint 负责编译器覆盖不到的那一档（格式、hooks、promise、import）——
  **分工口径跨仓一致，工具参数各仓自定**（分号、引号本就不同）。
- **本地钩子只跑秒级检查**（格式与 lint 的自动修复，以及不需要网络的测试）；typecheck 与需要网络或历史的测试留给 CI。
  意图：钩子一慢，就会有人用 `--no-verify` 绕过，等于没有钩子。
- CI 安装一律走 frozen 模式，不联网解析新版本。
- **每个可维护目录一对双件**：`AGENTS.md` 写「在这里要怎么干」，`README.md` 写「这里有什么、改哪」；
  同一事实只有一个 home，跨件只给指针。

### 3.6 发布态守卫与兼容巡检

- **发布态不变量**落成 `check:release` 脚本，发布流程在 publish **之前**跑它。脚手架模板带一份，新仓出生即满足这条判据；
  各仓在它后面**追加**自己的断言，不删里面任何一条。
- **发版噪声守卫**（`scripts/release-guard.mjs`）判的是「这段改动能不能改变 npm 上的产物」。**排除法**：认不出的路径
  一律算产物 —— 宁可漏判（多答一次），不误拦。
- **兼容巡检**对着**上游**动没动，本地提交改不了结论，所以按周跑、**不挂 `push`**。
- **声明了几族，就得验几族。** 声明是并集（`^a || ^b || ^c`）时，巡检必须判**每一条**，脚本按行打印计数。
  意图：两族并集若只跑了 `next`，就是「看着绿、实际只验了三分之二」—— 那正是声明存在的理由，**掉一条腿是缺陷，不是简化**。
- **测任何一族都必须把声明临时收窄到那一族** —— **不只是低族**。意图：不收窄会装出**混合树**，「换到某条线」这一步
  跑的根本不是那条线。机制 → [依据：并集声明下安装器按 `latest` 选族](../.agents/notes/2026-10-12-installer-picks-latest-family.md)。
- **收窄会撞上两条读 `package.json` 的红线**：族前缀这类值只写在机器输入行（矩阵值或 `run`），不写进 workflow 注释；
  跑 typecheck / build / test **之前**把清单还原成提交时的样子。意图：红线判的是**仓库的声明**，不是巡检里临时的收窄形态。
  论证 → [决策：compat 收窄只服务装与核对，跑测试前还原清单](../.agents/notes/2026-10-12-narrowing-and-redlines.md)。
- **只记录、不阻断的腿**：巡检的某条腿可以 `continue-on-error`，但必须在 workflow 里写明理由。意图：没有理由时，
  一条永远红的腿与一条永远绿的腿无法区分。
- **巡检红了的可见性**：定时任务的失败邮件只发给最后改过 cron 的人，不能当主通知 —— 失败要开或更新一条**固定标题**的
  tracking issue（同一处失败不重复刷评论）。

### 3.7 插件图标

包根一份 `icon.svg`，由 `"icon": "./icon.svg"` 声明，并进包的 `files`（第 4 节）。

- **画布 36×36**：`viewBox="0 0 36 36"`，`width` / `height` 与它一致。
- **透明底**：`<svg>` 写 `fill="none"`，且**不要有任何铺满画布的矩形**。意图：宿主把文件画在自己的底上，
  烘进去的背景会显示成一块色板。
- **判的是渲染后的几何，不是属性值。** 一个矩形是否「铺满画布」，要看它的**所有外层 `transform` 都应用之后**；
  而 `<defs>` 里的 `<rect>`（`clipPath`、`mask`、渐变）**不绘制任何东西**。这两个坑都是活的：
  一枚 `width`/`height` 很大的矩形可能是**裁切路径**；一枚底板可能坐在某个组里，被 `transform` 缩放平移后
  落进边距之内 —— 内缩、圆角、画布边缘保持透明，**完全合规**。
  用 grep 找 `<rect>` 再按数字判，会把这枚图标判错；要看它坐在哪个组里。
- **作为图形一部分的底板是允许的**，前提是它内缩、圆角、图形压在它上面 —— 这正是下面那条边距判据推得的结果。
  禁止的是**方角铺满**的矩形，那读起来是背景板，不是图形。
- **图形居中**，**紧的那条轴**上留 **7–9**。方形图形四边同距；宽扁或瘦高的图形是「信箱式」居中 ——
  紧的那条轴守住这个边距，另一条轴拿到居中之后的余量。
- **颜色烘死**。不用 `currentColor`、不用主题变量、不用 CSS：宿主按图片渲染，三者都不起作用。图形可以用自己的配色。
  **一段解释「为什么禁 `currentColor`」的注释不算违规。**
- **只放图形、渐变与滤镜**。不要脚本，不要外部引用。
- **XML 注释里不许出现连续两个连字符**（`--`）。出现后文件不再被当图片解析，宿主**静默**回落成默认图形。
- 支持的格式与体积上限是**宿主**的限制，不是我们的 —— 去宿主的插件参考里查，不要抄在这里。

### 3.8 发布流程

发布层的实现**各仓各写**（模板给一份满足下面四条的参考实现）。四条是行为底线：

| 底线 | 判据 |
|---|---|
| **手动与 tag 两个入口** | tag 触发带一道闸：tag 名必须等于 `v` + 清单版本号 |
| **发版说明读 Drafter 草稿** | 读不到或读空时回落 `--generate-notes`，且**读不到必须发 warning** |
| **发完删掉草稿** | 删的是 tag 不以 `v` 开头的那一个，正式版不动 |
| **用 OIDC 发 npm** | 全程不传 token；代价是 npm 后台配一次 Trusted Publisher |

四个容易漏、且漏了都**静默**的点：

- **tag 触发时守卫的基线要排除正在发的那个 tag。** 否则 `describe` 解析出它自己、`<tag>..HEAD` 恒空，
  一次完全正常的发布被判成「没有可发布的内容」。
- **「只接受 main」那道判定要带 `github.event_name` 守卫。** 不带的话 tag 触发时 `github.ref` 是
  `refs/tags/...`，每一次 tag 发布都红。
- **建 Release 之前先判存在。** 没有这道幂等，重跑撞 tag 已存在而红。
- **清洗草稿正文要按 action 名匹配那一整行**，不要抄提示语的全文 —— 那句话归组织仓模板所有，
  照抄一句就是一条静默失效的 sed。

**逐仓自己定、不强制的**：发版前的检查链、environment 名字、要不要 GitHub App token 推默认分支、
建 Release 的重试策略。这些的前置配置（labels、environments、secrets、ruleset、npm 后台）**都不在文件里**，
模板替不了，各仓的 `docs/PUBLISHING.md` 写自己那份。

**发布可以因为任何文件都修不了的原因失败。** 实际遇到的那一次：Trusted Publisher 绑定过期，OIDC 换发返回 404，
包**静默**停在旧版本上。这就是第 4 节要求「合并的版本必须真的发到 npm」、以及市场要报漂移的原因 ——
「合并了」与「发布了」之间的那段空档，从仓内部看不见。

### 3.9 各仓合法差异

形状相同，参数或数量不同。单看这些都不是缺陷；必须一致的东西在第 5 节。

| 什么可以不同 | 为什么允许 |
|---|---|
| 构建器：`tsdown`，或编译器加一个产出浏览器半边的脚本 | 两者都产宿主半边与浏览器半边；脚手架发的是 `tsdown` |
| `tsconfig` 的份数：每个编译目标一份 | 测试单独编译时才加测试配置 |
| `vitest` 配置的份数：有契约测试两份，没有一份 | 契约配置的存在就是为了把契约用例分开跑 |
| `compat.yml`：腿、目标、阻断还是只记录 | 各仓声明的族不同，历史不同 |
| `ci.yml` / `release.yml`：job、矩阵、步骤 | 除了收口 job 那条判据，没有别的东西跨仓读它们 |
| **不可不同**：草稿 Release 的 workflow | 第 2 节要求它相同 |

**当前值不要写进本文。** 各有几份、某个仓用哪个构建器，都是会变的**事实**：去仓里读，或用 `scaffold check` 比。
上面记录的是这些差异属于哪一**类**。

## 四、发出去的包必须带什么

市场读的是**已发布的产物**，从不读 checkout。所以它需要的东西必须活进 tarball 与 registry 清单。
漏掉不会让插件装不上 —— 但它的市场条目会**静默降级**：没标题、没图标、某个版本从列表里消失。

| 什么 | 从哪读 | 「缺了」长什么样 |
|---|---|---|
| `locale/<语言>.json`，含 `meta.title` 与 `meta.description`，**且必须有 `en`** | 已发布的 tarball | 条目显示包名而不是标题 |
| 图标文件，**由 `package.json` 的 `icon` 声明**，并由 `files` 打进包 | 已发布 tarball 里的声明路径 | 条目没有图标 |
| `engines.dsh` 是合法的 SemVer 区间，**不能是 `workspace:` 区间** | registry 清单 | 条目失去兼容区间，或被当成「任意版本」 |
| `author` | registry 清单 | 条目作者一行为空 |

另外两条义务，针对产物而不是仓：

- **合并进 `main` 的版本必须真的发到 npm。** 合并不等于发布；两者之间市场会继续宣传上一个版本，
  而本仓所有检查都正确且全绿。各仓的 `docs/PUBLISHING.md` 写明它怎么证明「发出去的就是合并的那个」。
- **只有发布才能改变上面任何一项。** 在仓里改清单，读者看到的东西不会变，直到发版。

**字段语义刻意住在别处**：哪个 JSON 键、哪个路径、读者遇到未定义成员怎么办 → 市场的
[market-format.md](https://github.com/dsh-plugin-lab/market/blob/main/docs/market-format.md)。
本节写**义务**，那份文档写**契约**，两边不互抄。

## 五、逐条判据（跨仓一致性）

**这一节才是要动手的地方。** 最后一列不是散文：它点名判这条的文件或脚本，所以「这条到底有没有被执行」
有答案，不靠感觉。第一到四节解释的是下面某行为什么成立，不必按顺序读。

三档的含义：

| 档 | 含义 |
|---|---|
| **必须一致** | 不一致即缺陷，必须变成一条检查 |
| **应当一致** | 判定逻辑共享，参数各仓自定 |
| **能力可选** | 规则确实不适用 —— **不是**被关掉了 |

| 判据 | 档 | 落点 |
|---|---|---|
| 发出去的包带上第 4 节的四项输入 | 必须一致 | 各仓 `check:release`（断言 tarball 与清单里有什么）；市场侧的 diagnostics 让遗漏可见 |
| 合并的版本真的发到 npm | 必须一致 | 各仓 `docs/PUBLISHING.md` 的发布后核对；全组织范围由市场的漂移报告发现 |
| 声明的每一族宿主都被巡检判过 | 必须一致 | 各仓 `scripts/check-declaration.mjs`，按行打印计数 |
| 锁文件里的 `resolved` 指向官方 registry | 必须一致 | 各仓一条红线断言（条数由脚本数，不写进文档） |
| **只用 pnpm**，`pnpm-lock.yaml` 是唯一锁文件 | 必须一致 | 模板里写明；迁移过的仓其 `.prettierignore` 由 `scaffold check` 对齐 |
| 缺同侪包 → 失败；只缺 dev → 警告并跳过 | 应当一致 | 判定逻辑共享（**默认失败**）；跟哪条宿主线由各仓定 |
| peer 与 dev 的版本必须一致 | 必须一致 | 各仓一条红线断言 |
| 四个编译器开关与 ESLint 各管一层 | 应当一致 | 各仓红线断言「开关存在」；**开关的值住 `tsconfig.json`**，工具参数各仓自定 |
| 发布态不变量 | 必须一致 | 各仓 `check:release`（模板带一份，各仓**只追加**不删）；纯宿主插件可对 `files` 一项豁免，**宿主兼容区间不可豁免** |
| 发布流程**不得**改写版本号 | 必须一致 | `check:release` 里的 `findVersionWrites`，**配反向控制**。改版本号是发布前的独立一步 |
| **手动与 tag 两个入口都能触发**，且 tag 触发时基线排除该 tag | 必须一致 | 各仓发布流程里的一条断言 |
| **正文读 Drafter 草稿**、**发完删草稿**，且**读不到时发 warning** | 必须一致 | 各仓发布流程里的一条断言。没有那条 warning，「发布成功但正文来自回落」就是静默失败 |
| **npm 发布走 OIDC**，全程不传 token | 必须一致 | 各仓发布流程；前置是 npm 后台的 Trusted Publisher（人做，模板带不了） |
| 发版前确认要发的那个提交已在**远端** | 必须一致 | 各仓 `docs/PUBLISHING.md` 的「发布之前」 |
| 一次发布产出的 git 侧产物形状相同（tag 形状、Release 存在、预发布标记） | 必须一致 | 各仓发布流程里的一条断言。tag 名是**机器**在读（守卫用 `git describe --match`），不是纯审美 |
| 宿主兼容声明必须**自洽**，且**整串在跨仓之间可比** | 必须一致 | 自洽由各仓红线断言；整串靠读各自已发布的清单比对。今天是否一致是每次要**重新测**的事实，不是抄进本文的值 |
| 判断依赖归哪一类的判据是「**我们与它的关系**」：只 `import type` → `devDependencies`；**消费它提供的服务** → `peerDependencies` | 必须一致 | 各仓 `AGENTS.md`。判据与现状冲突时，下一个人照判据删 |
| TypeScript 严格开关（`strict` / 索引访问 / 可选属性）的档位 | 应当一致 | **流程**共享：开任何开关前用**真实配置**（不是 CLI 覆盖）数一遍站点，两个一起开必须分开验；**参数按仓**，不做跨仓快照 |
| 兼容巡检里「只记录、不阻断」的项 | 必须一致 | 必须带理由，否则一次绿跑会盖住真问题 |
| 诊断性步骤（例如发布时打印凭据声明） | —— | 属落地实现：**局部于 workflow**，不抽 |
| 路径冲突断言 | —— | **不写**：等价保护已存在，第二份就是重复 |
| CSS 怎么注入、有没有样式表 | 能力可选 | 按仓：规则本身不适用 |
| Drafter 的**分类 → 标签映射** | 应当一致 | 组织仓那份是**默认值**；标签是仓的元数据，按仓设置 |
| 客户端 `inject` 只列真实依赖 | 必须一致 | 用官方自带的校验器，不要写散文 |
| 链接怎么写：**同仓 → 相对路径**；**跨仓（同组织或不同组织）→ 绝对 URL**；一律 `[]()`，不用 `<URL>`，不用裸 URL。作为**值**而不是引用的 URL 放行内代码 | 必须一致 | 各仓 `AGENTS.md`；渲染在组织主页上的文件是例外（那里的链接必须绝对 —— 见那个仓的 `AGENTS.md`） |

**两类内容，分开治理**：

- **断言**（写错 = CI 当场红，**响**）—— 优先。
- **知识**（写错 = 有人读到过期指南，**静**）—— 同一批，但不做成红线。

**一条兜底判据**：当某个仓过不去上游的**类型面**时，它**可以停在还能构建的那条线上** ——
能构建优先于跟线。这不与上面的判据冲突：上面说声明必须与推荐的那条线自洽，这条说自洽的目标可以是更低那条线。
停在不同线上的仓，不必强行对齐。

**为什么判据住在这里而不是某个仓里** → [决策：跨仓判据住组织仓](../.agents/notes/2026-10-12-criteria-live-in-the-org-repo.md)。

## 六、怎么核对

- **逐字节相同的副本** → 比字节，不比意思。执行体：`node scripts/scaffold.mjs check <repo>...`
  （模板那一份与各仓同名文件做 SHA-256 比对）。不一致**不必然是缺陷** —— 它报的是「知道它不同」，
  不是「强行一样」。哪些文件才是候选，看该脚本里的 `IDENTITY_FILES`。
- **形状** → 读本文的判据；不要把本文的值抄进仓。
- **一条规矩不能只活在散文里** → 能变成断言的都变成断言（红线测试、`check:*` 脚本）；散文只留指针。
- **对比式描述（「A 有、B 没有」）过期最快** → 它同时依赖两边，照它行动之前先回原始来源核实。
- **管理层设施自己核对**：组织仓没有 CI，靠手工跑（见它的 `AGENTS.md`）；市场有自己的 workflow、测试与
  diagnostics 基线（见它的 `AGENTS.md`）。第 5 节没有任何一行要求这两个仓去满足插件的义务。
