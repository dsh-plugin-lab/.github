# `check` 必须覆盖 CI 的每一步

**类型**：决策。
**状态**：生效

## 问题

模板里的 `pnpm run check` 跑 typecheck / build / test / check:release，而同模板的 CI `verify` job 跑
typecheck / build / test / lint / format:check。两个命令回答**同一个问题** ——「这样推安全吗」——
而模板把它们摆成同一道闸门，于是本地那个比它所代表的闸门**窄**。

差集里的两步恰好是「最便宜也最没用的时刻才发现」的那一类：源代码被脚本改过、没跑格式化，
类型仍然合法、测试仍然全过、`eslint` 也不管排版，只有推上去之后 `format:check` 才红。
`dsh-harness-dispatcher` 就是这么发现的：一次脚本编辑让 `check` 绿、推送红。

这不是违反了某条规则，而是**规则本身缺了一格**：`docs/criteria.md` 里最接近的两行分别管
「发布态不变量」与「CI 必须包含哪些步骤」，两行都没说这两者必须覆盖同一片地面。

## 决策

**模板 + 一条判据（案 B）**，两层一起改，因为只改模板只能修好**将来**生成的仓，改不了已经长歪的那几个：

1. 模板 `package.json` 的 `check` 补齐成
   `typecheck && build && test && lint && format:check && check:release`。
   顺序照 CI，`check:release` 放最后 —— 它是发布态守卫，属于「推之前」不属于「验证 job」。
2. `docs/criteria.md` 加一行 **Must agree**：有 `check` 脚本的仓，它必须覆盖 CI 跑的每一步。
3. 模板种一条红线 `test/check-parity.test.ts`，让新仓从第一天就守住；已存在的仓各补一条同形断言。

**判据只管一个方向。** 反方向（`check` 跑了 CI 不跑的步骤）**不是缺陷**：`check:release` 就该只在
推送前跑，硬要两边相等会把发布态守卫塞进验证 job。所以断言的形状是「CI ⊆ check」，
不是「CI = check」。

**没有 `check` 脚本的仓不在本条范围内。** 它没有对外做出「本地绿 = CI 绿」的承诺，
一条空指针的判据只会让这条规则看起来覆盖了六个仓、实际只管四类形状。

## 替代方案

- **只改模板（案 A）**：一行改完，没有判据成本。否决理由就是上面的第 1 条 ——
  它只修未来。而且模板本身就是「形状没写在任何地方、每个仓各自决定」的产物，
  不改判据，下一个仓还是会各自决定。
- **两个方向都断言（`check` = CI）**：看起来更严格，实际是错的。`check:release` 不属于 CI，
  强行相等会逼着把发布态守卫塞进 `verify` job，而那个 job 的职责是「这一版能不能构建」。
- **把 `check` 删掉、只留 CI**：省掉一处重复。但本地就再没有一条命令能回答「能不能推」，
  而 CI 的往返是分钟级；代价是把等待从本地移到远端，不是消除。
- **给没有 `check` 的两个仓新造一个**：这一轮不做。它们是另一种（也合法的）形状，
  加进去等于顺手改掉两个仓的开发循环，与这条判据无关。要加是独立的一次决定。

## 影响

- 模板那一处是**唯一的**来源：新仓生下来就是合规的，不需要谁记得。
- 已经长出 `check` 的四个仓，`check` 会变慢（多了 `lint` 与 `format:check`）——
  这正是它该跑的东西，慢的部分本来就在 CI 里跑过一遍。
- 红线读的是 `package.json` 与 `.github/workflows/ci.yml` 两份文件，
  所以**给 CI 加一步而忘了 `check`** 会当场红。反向不红，理由见上。
- 这条判据的执行体是一个必须**带反向控制**的断言：一个少了 `lint` 的 `check` 必须被抓住。
  「现在这条绿」与「这条判据有牙齿」是两件事，后者要单独证 ——
  首次实现时正是反向控制抓出了自己的 bug（正则要求 `- run:` 同行，于是 `format:check`
  在带 `name:` 的步骤里被漏读，覆盖断言少查了一步）。
